Lesson 4: Limits

Root cause analysis will help prevent just treating the symptoms

Click the Plus icon in the accordion below to review all information from the above video.

Limits are in place to ensure that a query or a series of queries will not render the LogScale instance to be un-usable to other users or crash the instance. There are a series of user configurable soft limits and non-user configurable hard limits.

Soft limits can be increased to allow specific resource-intensive queries to continue running. However, increasing soft limits almost always requires increasing corresponding hardware resources and it is ALWAYS a path to diminishing returns.

Thus, before increasing the soft limit, ask the question “Is this is a problem of the “lower” limit or is it a problem of an inefficient query?”

Example in the above video:

#event_simpleName = ProcessRollup2 | groupby([id], function=[tail(1)])

The size of the state necessary to run this query exceeds the per-query size quota. A partial (and possibly incorrect) result is reported. Please lower the limits used in the query, or rewrite the query in such a way that it uses less query state. Running it on a shorter time interval may also help.

In the above query, there are over 51,000 hits on unique id. Thus there are huge numbers of unique records being put into memory to process the groupBy() function. This caused the query to exceed the amount of resources that are available to run this query. The solution would be to add a limit to the groupBy(), for example groupBy([id], function=[tail(1)], limit=10). Adding limit=10 would limit the size of the result and keep it below the allocated resource limit.

Another example in the above video:

#event_simpleName = * | groupBy([id], function=[tail(1)])

groupBy exceeded the maximum number of groups (20000) and groups were discarded. Consider either adding a limit argument in order to increase the maximum or using the 'top' function instead.”

This query further causes the exhaustion of the resource limit. In this example, the culprit is the asterisk *.  On top of exceeding the per query resource limit, now we have exceed the maximum 20K limit. This is a soft limit associated with most aggregation query functions such as groupby() as there is an environment setting governing such soft limits to ensure users do not abuse available system memory and become a ‘noisy neighbour’ who degrades the user experience for other users of the system.

The solution is to assign a value to #event_simpleName = ProcessRollup2  so that the query is targeting specific files rather than mapping every file unnecessarily.
